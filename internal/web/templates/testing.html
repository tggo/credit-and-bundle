Credits & Bundles — як перевірити, що система витримує

  • MVP — тест уже є в bundle-credit-test, назва поруч. додати — у проді, ще не написано.
  • Головний інваріант, який звіряє кожен тест із грошима: credit_lots.remaining = Σ credit_ledger.delta по lot, і жоден lot не менше 0.
  • Тести на моках БД тут нічого не доводять: гонки, блокування й UNIQUE живуть у Postgres. Тому основа — інтеграційні тести на реальному Postgres з -race.

1. Unit — чиста логіка, без БД

  • Порядок списання lots: вужчий scope першим (bundle → platform), далі bonus перед paid, далі той, що раніше згорає, далі старший. додати як табличний тест; зараз покрито інтеграційним TestFlow_ScopeAndSpendOrder.
  • Формула refund: apps × частка невикористаного часу + credits × частка невитрачених кредитів. Межі: день 0, останній день, усе витрачено, нічого не витрачено, округлення підсумку до цента (math.Round). додати.
  • request_hash: той самий body з іншим порядком полів дає той самий хеш; інший input дає інший. додати.
  • Межі шарів: домен не імпортує інший домен напряму. MVP TestLayerRules, TestDomainsHaveIface.
  • Схема і Board не розходяться: кожна таблиця й колонка описана, поля й кардинальність на Board = схема. MVP TestBoardFieldsMatchSchema, TestBoardCardinalityMatchesSchema, TestEveryTableAndKeyColumnIsDescribed.

2. Integration — реальний Postgres, повні сценарії

Видача прав (grant handler)

  • Bundle → license на кожен plan item + один credit_lots зі scope на застосунки бандла. MVP TestFlow_ScopeAndSpendOrder.
  • Підписка з кредитами і без. MVP TestFlow_SubscriptionWithAndWithoutCredits.
  • In-app пакет працює лише у своєму застосунку. MVP TestFlow_InAppPackOnlyForItsApp.
  • Продовження зсуває licenses.due_date, старий lot згорає. MVP TestFlow_RenewalAndExpiry.
  • Дубль події, події не по порядку, refund раніше за paid. MVP TestWebhooks_OutOfOrderAndDuplicates, TestWebhooks_RefundBeforePaidIsParked, TestWebhooks_TerminalStateAndPastDue.

Списання (charge)

  • Провайдер 5xx → кредити повертаються в ті самі lots. MVP TestFlow_ProviderFailureRefundsSameLots.
  • Одне списання з двох lots. MVP TestRace_ChargeSpanningTwoLots.
  • 402 не зберігається як результат ключа: після поповнення той самий ключ проходить. MVP TestIdempotency_402IsNotStored.
  • Replay після відкликання ліцензії віддає збережений результат, не 403. MVP TestIdempotency_ReplayAfterLicenseRevoked.

Refund і sweeper

  • Частковий refund, refund після past_due не чіпає раніше оплачений період. MVP TestFlow_PartialRefund, TestFlow_RefundAfterPastDueKeepsEarlierPeriod.
  • Повернення у відкликаний або протермінований lot згорає, не оживляє його. MVP TestRefund_IntoRevokedLotIsBurned, TestRefund_IntoDrainedRevokedLotIsBurned, TestSweeper_RefundIntoExpiredLotIsBurned.
  • Процес впав після debit → sweeper повертає кредити. MVP TestSweeper_CrashAfterDebitReturnsCredits.
  • Втрачений webhook знаходить reconciliation. MVP TestReconcile_LostWebhookFound.

Контракт з Billing

  • Contract test на три події (PaymentSucceeded, PaymentRefunded, SubscriptionCanceled): схема полів, стабільний payment_id на повторах. додати, спільно з Billing.

3. Concurrency — те, що ламається лише під паралельністю

  • Один гаманець, N пристроїв одночасно: успішних рівно стільки, скільки вистачає кредитів, решта 402, баланс ніколи < 0. MVP TestRace_OneBalanceManyDevices.
  • Той самий Idempotency-Key паралельно: одне списання, решта 409 або replay. MVP TestIdempotency_SameKeyConcurrent.
  • Багато клієнтів одночасно — без deadlock (порядок блокувань: credit_accounts → lots за id). MVP TestRace_ManyCustomersNoDeadlock.
  • Refund паралельно зі списаннями. MVP TestRefund_RacesChargesWithoutDeadlock.
  • Запуск: go test -race -count=20 ./... — гонка, що проявляється раз на 20 прогонів, теж бага.

4. Load — чи тримає навантаження

  • Інструмент: k6 або vegeta на staging з копією схеми і реалістичними даними. додати; в MVP навантажувальних тестів немає.
  • Профіль 1, звичайний: багато клієнтів, у кожного свій гаманець. Мета: p99 POST /charges без провайдера < 50 мс на цільовому RPS. Провайдер мокаємо з затримкою 1–10 с, щоб міряти нашу частину.
  • Профіль 2, гарячий гаманець: 50+ паралельних запитів в один credit_accounts. FOR UPDATE робить їх послідовними — міряємо, з якого паралелізму ростуть таймаути. Очікувано нормально: транзакція коротка, провайдер поза нею.
  • Профіль 3, сплеск продовжень: тисячі PaymentSucceeded на початку місяця. Міряємо лаг від події до видачі прав.
  • Soak 1–2 год: ріст credit_ledger, пул з'єднань pgx, кількість in_progress не росте.
  • Після кожного прогону — той самий інваріант: Σ журналу = залишки.

6. Міграція

  • Shadow compare на етапі «Read items»: старий і новий шлях рахують права кожного клієнта, розбіжність логуємо. Ворота: 0 розбіжностей за 7 днів.
  • Backfill на копії проду: кількість licenses до = після, жоден активний клієнт не втратив доступ.
  • Rollback кожного кроку прогнаний на staging до проду. Деталі в Migration.

7. Що моніторити

Гроші — page (будимо людину)

  • Розбіжність credit_lots.remaining ≠ Σ credit_ledger.delta: > 0 → page. Нічний job по всіх lots, плюс по змінених за годину.
  • Платіж без виданих прав > 5 хв: page. Звірка payments з licenses/credit_lots по payment_id.
  • Від'ємний credit_lots.remaining: page (CHECK має не дати, але перевіряємо).

Надійність — alert

  • credit_charges в in_progress > 5 хв: alert — sweeper не працює.
  • Частка 502 від провайдера > 5% за 15 хв: alert, перемкнути провайдера.
  • Лаг обробки подій Billing (час події → видача прав) p99 > 1 хв; черга retry росте.
  • Розбіжності reconciliation з Billing > 0 після нічного прогону.
  • Postgres: lock wait на credit_accounts, deadlocks > 0, пул з'єднань > 80%.

API — RED-метрики на кожен endpoint

  • Rate, errors, duration для POST /charges і GET /balance, окремо наша частина і провайдер.
  • Розбивка по кодах: ріст 409 lot_changed_retry = гарячі гаманці; ріст 422 = клієнт неправильно генерує ключі; ріст 403 no_active_license = збій видачі прав.

Бізнес — дашборд, тижневий огляд

  • Собівартість AI / виручка по кожній дії (action_code) — чи ціна в action_prices покриває провайдера.
  • Згорілі кредити: скільки куплено і не витрачено до expires_at.
  • Частка refund і chargeback по offering.

Credits & Bundles — міграція даних

  • Мета: перейти з поточної моделі (offering = один plan) на offering з items, без даунтайму і без перевипуску ключів ліцензій.
  • Принцип: expand → contract. Спершу тільки додаємо, читаємо з нового за флагом, і лише в кінці видаляємо старе.
  • Для чинних клієнтів нічого не змінюється: ті самі subscriptions, ті самі licenses.key, наступне продовження йде по тому самому offering — тепер це offering з одним item.
  • Кожен крок має умову переходу (gate) і спосіб відкату. Відкат неможливий лише на останньому кроці.

Що було і що стане

plans

  • Було: id, application_id, name, slot_count, licensing_model, trial_period, grace_period.
  • Стане: trial_period і grace_period переїжджають в offerings.trial_days / grace_days. Решта без змін.
  • Старі колонки видаляємо лише на кроці Contract.

offerings

  • Було: id, plan_id, price (decimal), billing_period.
  • Додаємо: name, kind (single | bundle | credit_pack), price_minor (bigint), currency, trial_days, grace_days, status.
  • Міняємо: plan_id стає nullable (у бандла і пакета кредитів його немає), на кроці Contract видаляємо.
  • Міняємо: price decimal → price_minor цілі центи; decimal видаляємо на кроці Contract.
  • billing_period отримує CHECK: month | one_time.

offering_items — нова

  • offering_id → offerings.id; рівно одне з plan_id → plans.id або credit_package_id → credit_packages.id.
  • allocation_weight, quantity, item_type.
  • На час міграції — UNIQUE (offering_id, plan_id): на ньому тримається ідемпотентність backfill.

credit_packages, action_prices — нові, порожні

  • Даних для перенесення немає. Наповнюються, коли вмикаємо кредити.

subscriptions і payments — зона Billing

  • Було: subscriptions.next_billing_at, subscriptions.payment_ref — один платіж на підписку.
  • Стане: subscriptions.kind (recurring | one_time), current_period_start / current_period_end; платежі — окрема payments, рядок на період.
  • Це робить команда Billing. Нам від них треба: стабільний payment_id, події PaymentSucceeded / PaymentRefunded / SubscriptionCanceled, kind = one_time для пакетів кредитів.
  • Для чинних підписок Billing створює по одному рядку payments на поточний оплачений період (з payment_ref і next_billing_at) — інакше рефанд поточного періоду не знайде lots і межі періоду.

licenses

  • Було: id, subscription_id, customer_id, key UK, status, due_date.
  • Додаємо: offering_item_id → offering_items.id, application_id → applications.id.
  • Додаємо: UNIQUE (subscription_id, offering_item_id), індекс (customer_id, application_id) WHERE status = 'active'.
  • key, status, due_date не чіпаємо.

Credits — нові, порожні

  • credit_accounts, credit_lots, lot_scope_apps, credit_charges, credit_ledger.
  • Історичних кредитів немає. Єдиний backfill — credit_accounts на кожного чинного клієнта.

Крок 0. Підготовка

  • Feature flags, всі вимкнені:
    • catalog.write_items — новий код пише items;
    • catalog.read_items — читання складу з items, по застосунках;
    • catalog.shadow_compare — читати обома шляхами і порівнювати;
    • sales.bundles, sales.credit_packs — продаж нових offerings;
    • credits.gateway — списання, по застосунках.
  • Почати інвентаризацію читачів offerings.plan_id (див. крок 5) вже зараз — вона найдовша.
  • Знімок прод-бази для репетиції: увесь сценарій спершу проганяємо на копії і міряємо час backfill.
  • Дашборд міграції: лічильники з gate-запитів нижче.

Крок 1. Expand — схема

  • Усі зміни сумісні зі старим кодом: тільки нові таблиці і nullable-колонки, нічого не видаляємо.
  • Онлайн, без довгих блокувань:
    • ADD COLUMN без default або з константним default — миттєво (Postgres 11+);
    • індекси — CREATE INDEX CONCURRENTLY;
    • FK і CHECK — NOT VALID, потім окремо VALIDATE CONSTRAINT (не блокує запис);
    • SET lock_timeout = '3s' на кожну DDL, щоб не стати в чергу за довгою транзакцією.
CREATE TABLE offering_items (...);  CREATE TABLE credit_packages (...);  CREATE TABLE action_prices (...);
CREATE TABLE credit_accounts (...); credit_lots, lot_scope_apps, credit_charges, credit_ledger

ALTER TABLE offerings ADD COLUMN name text, ADD COLUMN kind text, ADD COLUMN price_minor bigint,
  ADD COLUMN currency text, ADD COLUMN trial_days int, ADD COLUMN grace_days int,
  ADD COLUMN status text DEFAULT 'active';
ALTER TABLE offerings ALTER COLUMN plan_id DROP NOT NULL;

ALTER TABLE licenses ADD COLUMN offering_item_id uuid, ADD COLUMN application_id uuid;
ALTER TABLE licenses ADD CONSTRAINT licenses_item_fk FOREIGN KEY (offering_item_id)
  REFERENCES offering_items(id) NOT VALID;
CREATE UNIQUE INDEX CONCURRENTLY offering_items_offering_plan ON offering_items (offering_id, plan_id);
CREATE INDEX CONCURRENTLY licenses_customer_app ON licenses (customer_id, application_id)
  WHERE status = 'active';
  • Gate: міграція на проді, старий код працює, помилок у логах немає.
  • Відкат: DROP нових таблиць і колонок — їх ще ніхто не читає і не пише.

Крок 2. Dual-write — новий код пише в обидва місця

  • Вмикається до backfill. Інакше offering чи ліцензія, створені між backfill і dual-write, лишаться без item.
  • Що пише новий код:
    • створення offering для одного застосунку — offerings.plan_id і рядок offering_items, в одній транзакції;
    • зміна ціни — і price, і price_minor;
    • видача ліцензії — licenses.offering_item_id і application_id;
    • trial / grace — у plan і в offering.
  • Читаємо ще по-старому, з plan_id.
  • Деплой коду до вмикання флага: спершу всі інстанси вміють писати, потім флаг catalog.write_items.
  • Gate: флаг увімкнено на всіх інстансах; нові offerings і ліцензії за останню добу мають items (запит нижче).
  • Відкат: вимкнути флаг. Зайві items нікому не заважають.
-- нові ліцензії без item після вмикання флага — має бути 0
SELECT count(*) FROM licenses l JOIN subscriptions s ON s.id = l.subscription_id
WHERE l.offering_item_id IS NULL AND s.created_at > :flag_on_at;

Крок 3. Backfill — старі дані в нові поля

  • Скрипт ідемпотентний: ON CONFLICT DO NOTHING і WHERE … IS NULL. Можна зупинити й перезапустити.
  • Батчами по ~1000 рядків за id, кожен батч — окрема коротка транзакція, пауза між батчами. Без одного великого UPDATE.
  • Порядок важливий: спершу offerings і items, потім ліцензії (їм потрібен item).

3a. Offerings

UPDATE offerings o SET
  price_minor = round(o.price * 10 ^ :currency_exponent),   -- USD 2, JPY 0
  currency    = :currency,
  kind        = 'single',
  name        = p.name,
  trial_days  = p.trial_period,
  grace_days  = p.grace_period
FROM plans p
WHERE p.id = o.plan_id AND o.price_minor IS NULL AND o.id BETWEEN :from AND :to;
  • Валюта: якщо ціни в різних валютах — брати з того місця, де вона зараз зберігається; експонента валюти з ISO 4217, не завжди 2.
  • Перевірка округлення: price_minor / 10^exp = price для кожного рядка, розбіжність → в окремий звіт, руками.

3b. Offering items — по одному на кожен offering

INSERT INTO offering_items (offering_id, item_type, plan_id, quantity, allocation_weight, code)
SELECT o.id, 'plan', o.plan_id, 1, o.price_minor, o.code || ':plan'
FROM offerings o
WHERE o.plan_id IS NOT NULL AND o.id BETWEEN :from AND :to
ON CONFLICT (offering_id, plan_id) DO NOTHING;
  • allocation_weight = уся ціна: item один.

3c. Licenses

UPDATE licenses l SET
  offering_item_id = i.id,
  application_id   = p.application_id
FROM subscriptions s
JOIN offering_items i ON i.offering_id = s.offering_id AND i.item_type = 'plan'
JOIN plans p ON p.id = i.plan_id
WHERE s.id = l.subscription_id AND l.offering_item_id IS NULL AND l.id BETWEEN :from AND :to;
  • key, status, due_date не чіпаємо — клієнт нічого не помічає.
  • Після backfill: VALIDATE CONSTRAINT licenses_item_fk, потім UNIQUE (subscription_id, offering_item_id) через CREATE UNIQUE INDEX CONCURRENTLY + ADD CONSTRAINT … USING INDEX.
  • NOT NULL на offering_item_id і application_id: CHECK (… IS NOT NULL) NOT VALID → VALIDATE → SET NOT NULL (Postgres 12+ бере перевірку з CHECK і не сканує таблицю).

3d. Credit accounts

INSERT INTO credit_accounts (customer_id) SELECT id FROM customers WHERE id BETWEEN :from AND :to
ON CONFLICT (customer_id) DO NOTHING;
  • Нові клієнти після цього отримують гаманець при реєстрації (той самий dual-write).

Gate кроку 3 — усі запити мають повернути 0

SELECT count(*) FROM offerings o WHERE o.plan_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM offering_items i WHERE i.offering_id = o.id);
SELECT count(*) FROM offerings WHERE price_minor IS NULL;
SELECT count(*) FROM licenses WHERE offering_item_id IS NULL OR application_id IS NULL;
SELECT count(*) FROM licenses l JOIN offering_items i ON i.id = l.offering_item_id
  JOIN subscriptions s ON s.id = l.subscription_id WHERE i.offering_id <> s.offering_id;
SELECT count(*) FROM customers c WHERE NOT EXISTS (SELECT 1 FROM credit_accounts a WHERE a.customer_id = c.id);
  • Відкат: нові поля ще ніхто не читає — можна обнулити й перезапустити.

Крок 4. Читання з нового за флагом

  • Спершу catalog.shadow_compare: кожен запит читає обома шляхами, відповідає старим, розбіжність → лог з id і метрика.
  • Що порівнюємо:
    • перевірка доступу: старий шлях через subscription → offering → plan, новий — licenses (customer_id, application_id);
    • вітрина: ціна і склад offering;
    • продовження: що видати по оплаті — один plan чи items;
    • trial / grace: з plan чи з offering.
  • Потім catalog.read_items: 1–2 застосунки → 10% → усі. Тиждень на кожному рівні або менше, якщо розбіжностей 0.
  • Gate: флаг на всіх, 0 розбіжностей за тиждень.
  • Відкат: вимкнути catalog.read_items, dual-write продовжує тримати старі поля актуальними.

Коли вмикати бандли і кредити

  • Offering бандла має plan_id = NULL. Будь-який старий читач plan_id на ньому впаде або покаже порожнє.
  • Тому sales.bundles — лише після кроку 5 (усі читачі на items), або обмежено: бандл видно тільки на вітрині, яка вже читає items, і тільки для внутрішніх акаунтів.
  • sales.credit_packs — коли Billing вміє kind = one_time.
  • credits.gateway — окремо: 1–2 застосунки одного вендора, один провайдер → тиждень без розбіжностей credit_lots.remaining ≠ сума credit_ledger.delta → решта.
  • Старі версії застосунків без Gateway AI-функцій не бачать — нічого не ламається.

Крок 5. Inventory — хто ще читає старе

  • Знайти всіх читачів offerings.plan_id, offerings.price, plans.trial_period / grace_period, subscriptions.payment_ref / next_billing_at:
    • пошук по коду всіх репозиторіїв;
    • pg_stat_statements: запити, що згадують ці колонки, і з якої ролі БД;
    • BI: views, ETL, дашборди;
    • панелі вендорів, саппорт-тули, шаблони листів («ваша підписка на X продовжена»), експорти бухгалтерії.
  • Кожен переходить на items. Для тих, кого не встигаємо переписати, — тимчасовий view offering_primary_plan (перший plan item), з датою видалення.
  • Окремий DB-юзер на кожного споживача, щоб у pg_stat_statements було видно, хто ще читає.
  • Gate: тиждень без жодного запиту до старих колонок, 0 розбіжностей.

Крок 6. Contract — видалення старого

  • Перед кроком: бекап / знімок, вимкнути dual-write у коді (деплой), переконатися, що старі колонки ніхто не пише.
ALTER TABLE offerings DROP COLUMN plan_id, DROP COLUMN price;
ALTER TABLE plans     DROP COLUMN trial_period, DROP COLUMN grace_period;
-- Billing у своїй зоні: subscriptions.payment_ref, subscriptions.next_billing_at
ALTER TABLE offerings ALTER COLUMN price_minor SET NOT NULL, ALTER COLUMN kind SET NOT NULL,
  ADD CONSTRAINT offerings_kind_chk CHECK (kind IN ('single','bundle','credit_pack')) NOT VALID;
DROP INDEX offering_items_offering_plan;   -- або лишити як бізнес-правило
  • Назад уже ніяк — тому gate стоїть перед кроком, а не після.
  • Видалені поля відновлюються лише з бекапу.

Чинні клієнти — що з ними відбувається

  • Активна підписка: продовжується по тому самому offering; Billing надсилає PaymentSucceeded, License по UK (subscription_id, offering_item_id) лише подовжує due_date існуючої ліцензії.
  • Підписка в trial: trial_days скопійовано з plan — trial закінчується тоді ж, коли й був би.
  • Підписка в grace / past_due: поведінка та сама, grace_days з plan.
  • Скасована, але оплачена до кінця періоду: ліцензія живе до due_date, як і раніше.
  • Рефанд поточного періоду після міграції: потрібен рядок payments за цей період — його створює Billing у своїй міграції.
  • Ключі ліцензій і десктоп-клієнти: нічого не змінюється, перевипуску немає.
  • Перехід з одиночної підписки на бандл: спершу видати права бандла, потім закрити стару підписку з прорейтом — доступ не переривається. Дві ліцензії на той самий застосунок на мить — нормально, доступ є, поки активна хоч одна.

Що може піти не так

  • Offering без plan у старих даних (битий рядок) — backfill пропускає, gate 3 показує, руками.
  • Ліцензія, чия підписка посилається на видалений offering — те саме, звіт і руками.
  • Округлення ціни при переході з decimal — звіт розбіжностей у 3a, жодного автоматичного округлення без перевірки.
  • Довга транзакція тримає lock під час DDL — lock_timeout і повтор.
  • Backfill навантажує репліки — батчі з паузою, стежимо за replication lag.
  • Новий запис, що проскочив між backfill і dual-write — неможливий, бо dual-write вмикається раніше; про всяк випадок gate 3 після повторного прогону backfill.
  • BI, що читає plan_id і не знайдений на кроці 5, — зламається на Contract. Захист: тиждень тиші в pg_stat_statements.

Моніторинг на час міграції

  • Прогрес backfill: скільки рядків без item / без price_minor лишилось.
  • Розбіжності shadow compare: кількість і приклади id.
  • Помилки перевірки доступу (403 на клієнтів, які мали доступ) — головний сигнал, що щось не так.
  • Платіж без виданих прав > 5 хв — page.
  • Replication lag під час backfill.
  • Після вмикання кредитів: credit_lots.remaining ≠ сума credit_ledger.delta — page.
